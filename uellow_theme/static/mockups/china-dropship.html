1 الملخص التنفيذي

لماذا هذه الخطوة، وما القرار الجوهري الذي يحمي نظامك.

الفرصة

كتالوج لا نهائي بلا مخزون

ملايين المنتجات من AliExpress/CJ تُعرض للعميل الكويتي دون شرائها مسبقاً أو تخزينها — رأس مال شبه صفري وتنويع هائل.

التحدي

تضخّم قاعدة البيانات

استيراد الملايين كمنتجات Odoo حقيقية = عشرات ملايين الصفوف وآلاف الجيجابايت صور → يشلّ النظام. هذا ما نتجنّبه بالكامل.

الحل

اعرض ولا تخزّن

نموذج خفيف منفصل + صور روابط خارجية + إنشاء منتج حقيقي «لحظة الطلب فقط». قاعدتك تنمو بعدد الطلبات لا المعروضات.

القرار الجوهري: ابدأ على التطبيق فقط (صفر مخاطرة SEO + جمهور مسجّل + حماية للبراند)، على website دروبشيبنج معزول (أول واجهة = «China Bazaar»، وتقدر تضيف واجهات/مناطق أخرى لاحقاً)، عبر موديول عام مستقل uellow_dropship لا يلمس أي منتج حالي. الويب لاحقاً على subdomain منفصل مع noindex.
لماذا «عام» لا «صيني»: المصدر (مزوّد) والواجهة (متجر/منطقة) كلاهما مجرد إعداد. اليوم AliExpress + China Bazaar؛ غداً CJ + واجهة أخرى، أو مورّد محلي — بلا إعادة كتابة الموديول.

النموذج الخفيف

dropship.product

  • ali_id — معرّف المصدر (index فريد)
  • title_en / title_ar — عنوان ثنائي
  • price_source → price_sell (computed بالهامش)
  • image_url — رابط خارجي/Bunny proxy (لا ir.attachment)
  • category / attrs — JSON خفيف
  • state — draft / listed / materialized
  • بلا mail.thread · بلا variants · بحث SQL مباشر
العزل الكامل

لا مساس بكتالوجك

  • موديول مستقل uellow_dropship
  • website دروبشيبنج مستقل (مثل «China Bazaar») — منتجاته تظهر فيه فقط
  • عند materialize: is_dropship=True · type=consu بلا مخزون · default_code=DS-*
  • لا يظهر في بحث/تصنيفات/ريلز/تطبيق Uellow الحالي
  • القاعدة تنمو بعدد الطلبات الفعلية فقط
مقارنة الحجم: استيراد كامل لمليون منتج ≈ 10–15 مليون صف + آلاف الجيجابايت. أسلوبنا: مليون صف خفيف في جدول واحد معزول (يُقلَّم دورياً) + صفوف حقيقية = عدد الطلبات فقط.

4 طبقة المزوّدين المرنة (Provider-Agnostic)

المتطلب الأساسي: الموديول لا يرتبط بـ AliExpress وحده — بل بواجهة adapter موحّدة تستوعب أي مزوّد دروبشيبنج بتغيير إعداد فقط.

المبدأ: نُعرّف واجهة connector قياسية واحدة (6 دوال). كل مزوّد = ملف adapter يترجم بين هذه الواجهة وبين API المزوّد الفعلي، ويُطبّع رده إلى مخطط dropship.product الموحّد. إضافة مزوّد جديد = adapter جديد فقط، دون لمس الواجهة أو التطبيق.

Registry

سجلّ المزوّدين

dropship.provider يسجّل كل adapter بـ code (aliexpress/cj/spocket/custom) + بيانات اعتماد + تفعيل/إيقاف — يُختار عند الاستيراد والطلب.

Routing

توجيه لكل فئة

مزوّد أساسي + احتياطي لكل فئة (نفس نمط توجيه مزوّدي Beena): لو فشل الأساسي أو ارتفع سعره → يتحوّل للاحتياطي تلقائياً.

Normalizer

طبقة التطبيع

6 البيزنس بلان

النموذج التشغيلي والتموضع والدفع والعمليات.

التموضع

براند فرعي

«China Bazaar» داخل Uellow — توقّعات منفصلة (سعر أقل/شحن أطول) تحمي براند Uellow الأصلي.

الجمهور

الباحث عن السعر

عميل يقبل الانتظار مقابل تنوّع وسعر أرخص — شريحة مختلفة عن عميل Uellow السريع.

الدفع

مسبق فقط

KNET/UPayments فقط — لا COD على الدروبشيبنج (يحمي من رفض الاستلام بعد الدفع للمورّد).

التوريد

API + تلقائي

طلب المورّد يُنشأ آلياً بعنوان العميل، مع رقم تتبّع يُدفع للتطبيق تلقائياً.

مصادر التوريد المقترحة

  • AliExpress Dropshipping API — الأوسع، يحتاج اعتماد شراكة
  • CJ Dropshipping — API أنظف + مستودعات + جودة أفضل
  • Spocket / خيارات إقليمية — لتقليل مدة الشحن

سياسة العميل (شفافة)

  • شارة مدة الشحن على كل منتج قبل الشراء
  • تتبّع الطلب داخل التطبيق
  • استرداد بلا إرجاع للقيم الصغيرة
  • إخطار فوري لو تغيّر السعر/نفد قبل التأكيد

7 خطة التنفيذ المرحلية (آمنة على الإنتاج)

تدرّج يقيس الأداء قبل التوسّع — صفر أثر على الحالي.

المرحلة 0 — البنية المعزولة
موديول عام uellow_dropship + نموذج dropship.product + واجهة متجر أولى قابلة للتهيئة (مثال «China Bazaar») + شاشة إعدادات (هامش، حدود، مزوّد، فلاتر). صفر تأثير على الكتالوج.
المرحلة 1 — استيراد تجريبي
فئة واحدة، بضع مئات منتجات، بحث SQL، عرض على واجهة China. نقيس الأداء وحجم DB.
المرحلة 2 — Materialize + الطلب
تحويل عند الشراء + ربط UPayments (مسبق) + رسائل مدة الشحن + إنشاء طلب المورّد.
المرحلة 3 — المزامنة والتوسّع
cron مزامنة سعر/مخزون (fail-closed) + رفع العدد تدريجياً + مراقبة الحجم + تتبّع الشحنات.
المرحلة 4 — تبويب التطبيق + الإطلاق
واجهة «China Bazaar» في التطبيق (إصدار جديد + AAB) + إطلاق beta لشريحة ثم للجميع.
لاحقاً — الويب (اختياري)
subdomain منفصل china.uellow.com + noindex لحماية SEO دومينك الأصلي.

9 موكاب التطبيق — «Dropship Mode» تحوّل كامل

أيقونة في الهيدر تبدّل التطبيق بالكامل إلى وضع الدروبشيبنج (واجهة المتجر الحالية، مثل China Bazaar): الرئيسية، الأقسام، السلة، الإعدادات — كل شيء يتحوّل. ضغطة أخرى يعود Uellow الأصلي.

الفكرة: ليس مجرد تبويب — بل مفتاح وضع (mode switch) عام. الحالة محفوظة في app_mode = uellow | dropship؛ كل شاشة تقرأ الوضع وتبدّل مصدر البيانات (X-Website-Id لواجهة الدروبشيبنج)، اسم الواجهة والشارات حسب الدولة الفعّالة، والأقسام والفلاتر والإعدادات — مع الحفاظ على نفس تصميم Uellow الحالي (أصفر/داكن) في كل الأوضاع. تجربة «تطبيق داخل تطبيق» غير مقيّدة بمصدر واحد.

لماذا شبكة الدول؟

  • وضوح فوري: كل دولة/مصدر ببلاطة وعلم — العميل يرى الخيارات كلها دفعة واحدة.
  • Uellow محلي مميّز: بلاطة صفراء كاملة العرض في الأعلى (الافتراضي والأهم).
  • World = مختصر: بلاطة «الكل» لمن يريد التصفّح عبر كل الدول معاً.
  • ديناميكي: كل بلاطة = storefront في الإعدادات (علم/اسم/مزوّد/عدّاد منتجات) — تُضاف دولة جديدة ببلاطة تلقائية بلا كود.
  • عدّاد حيّ: رقم المنتجات على كل بلاطة يبني الثقة ويبرز الغنى.
  • توسّع سلس: الشبكة تكبر تلقائياً؛ 8 دول أو 20 نفس التصميم.
  • China Hub: بلاطة مميّزة كاملة العرض أسفل الشبكة — وجهة الصين الكبرى (منتقى + أقسام خاصة)، والصين موجودة أيضاً كدولة عادية ضمن الشبكة.
  • ذكاء: تُعرض أول تشغيل + رابط «الدول» في الهيدر للعودة إليها أي وقت.

10 آلية العمل بالتفصيل (End-to-End)

رحلة كاملة من تصفّح العميل حتى وصول الطلب — مع توضيح مَن يفعل ماذا، ولحظة إنشاء المنتج الحقيقي.

1 · العميل يتصفّح التطبيق ← الموديول
التطبيق يطلب قائمة من dropship.product (بحث SQL مفهرس على ملايين الصفوف الخفيفة). لا استعلام على product.template، لا ORM prefetch. الصور روابط خارجية.
2 · يفتح منتجاً الموديول ← المزوّد
provider.get_product(id) + get_freight(الكويت) لحظياً → تُطبَّع وتُعرض: السعر بالدينار (بعد الهامش)، مدة الشحن، الألوان/المقاسات.
3 · يضيف للسلة → Materialize اللحظة الحاسمة
الآن فقط يُنشأ product.template حقيقي واحد (idempotent بمفتاح provider+source_id) بـ is_dropship=True, DS-*, بلا مخزون. القاعدة تنمو بمنتج واحد لكل طلب فعلي.
4 · الدفع المسبق UPayments
دفع كامل (سلعة + شحن) قبل الطلب من المورّد. لا COD. عند التحصيل يتأكّد الطلب.
5 · الطلب من المورّد الموديول ← المزوّد
provider.place_order(items, عنوان العميل) تلقائياً (أو مراجعة يدوية اختيارية). يُخزَّن رقم طلب المورّد على sale.order.
6 · التتبّع cron + إشعارات
get_tracking() يجلب رقم/حالة الشحنة → يُدفع للعميل عبر نظام الإشعارات الحالي (push_event) + يظهر في «طلباتي».
7 · الوصول والإغلاق تسليم
وصول الشحنة → تحديث الحالة → إغلاق الطلب. سياسة «استرداد بلا إرجاع» للقيم الصغيرة عند الحاجة.
8 · المزامنة الدورية حارس fail-closed
cron يحدّث السعر/المخزون: نفد المصدر أو ارتفع فوق الهامش → المنتج يُخفى فوراً + إعادة تسعير آلية عند تغيّر سعر الصرف/المصدر.
الأداء

لماذا لا تتضخّم القاعدة

الملايين في جدول خفيف واحد مفهرس (يُقلَّم). المنتجات الحقيقية = عدد الطلبات فقط. النسخ الاحتياطي والبحث يبقيان رشيقين.

التطبيع

مخطط موحّد

كل مزوّد يردّ JSON مختلفاً → طبقة Normalizer تحوّله لمخطط dropship.product واحد. التطبيق لا يعرف المزوّد.

الأمان التجاري

لا بيع بخسارة

حد أدنى للهامش + إخفاء آلي + إعادة تسعير + دفع مسبق = هامشك محمي ومخاطرة رأس المال ≈ صفر.

12 كيف يُقدَّم للناس (Go-to-Market)

التموضع، رسائل الإطلاق، القنوات، وبُناة الثقة — لتقديم مقنع يقلّل التردّد ويحمي البراند.

بيان التموضع: «لعملاء Uellow الباحثين عن تنوّع لا نهائي وأسعار أقل ولا يمانعون انتظاراً أطول — Uellow World يفتح ملايين المنتجات عالمياً بسعر شامل (يتضمّن الشحن والجمارك) وضمان وصول، داخل نفس تطبيق Uellow الموثوق.»
رسالة 1

تنوّع لا نهائي

«ملايين المنتجات من كل العالم» — ما لا تجده محلياً تجده هنا.

رسالة 2

سعر شامل

«السعر يشمل الشحن والجمارك — لا مفاجآت عند الاستلام».

رسالة 3

ضمان الوصول

«لم يصل؟ استرداد تلقائي» — يزيل خوف الشراء من الخارج.

رسالة 4

داخل Uellow

«نفس التطبيق، نفس الثقة، نفس نقاط الولاء» — لا تطبيق غريب.

مراحل الإطلاق

Soft beta — تفعيل لشريحة صغيرة (5–10%) + فئة واحدة؛ قياس التحويل ومدة الشحن الفعلية والمرتجعات.
إطلاق موجّه — بانر داخل Uellow + إشعار + صفحة الدخول (شبكة الدول) لمن أبدوا اهتماماً.
إطلاق عام — لكل المستخدمين + حملة تسويق + ربط بالمراجعين/المؤثرين (uellow_reviewers).
توسّع — دول/مزوّدون جدد + «Trending World» + رادار الطلب لتحويل الرابحين لمخزون Uellow.

13 أفكاري الإضافية (قيمة تنافسية)

أفكار من عندي تحوّل الدروبشيبنج العادي إلى ميزة تخصّ Uellow.

💱

تسعير ذكي بالدينار

محرك هامش لكل فئة + تقريب نفسي للسعر (7.900 بدل 7.83) + تحديث تلقائي عند تغيّر سعر المصدر أو الصرف.

🤖

Beena تترجم وتنقّي

عناوين AliExpress ركيكة → Beena تعيد صياغتها EN+AR نظيفة عند الـmaterialize، وتُخفي المقلّد آلياً.

⭐

فلتر «الأفضل فقط»

لا نعرض الملايين عشوائياً — فلترة على تقييم المصدر + عدد المبيعات + وقت الشحن، فيرى العميل منتقى لا فوضى.

📦

تجميع الشحنات

طلبات متعددة لنفس العميل خلال نافذة زمنية تُجمَّع في شحنة واحدة لتقليل كلفة الشحن ورفع الهامش.

🔔

تتبّع تلقائي في التطبيق

رقم التتبّع من المورّد يُدفع للعميل عبر نظام الإشعارات الحالي (push_event) + تحديثات المراحل.

🧪

مختبر المنتجات الرابحة

لوحة تكتشف المنتجات الأعلى تحويلاً في World ثم تقترح شراءها فعلياً كمخزون Uellow — الدروبشيبنج كأداة اكتشاف طلب.

أفكار جديدة إضافية

🎯

عالم ثالث قابل للإضافة

البنية تدعم أكثر من «عالم»: World (عالمي) · Local Vendors (بائعون محليون) · Wholesale (جملة). كل عالم = واجهة + مزوّد، تُضاف من الإعدادات.

⏱️

عدّاد شحن حيّ

«يصل خلال 14 يوم» يتحدّث لكل عميل حسب عنوانه وسرعة المزوّد — شفافية تقلّل النزاعات وترفع الثقة.

🛡️

ضمان World

تأمين بسيط اختياري بسعر رمزي: لم يصل خلال X يوم = استرداد تلقائي. يزيل حاجز «الخوف من الشراء من الخارج».

💬

Beena مرشد World

«ابحث لي عن سماعات تحت 5 د.ك تصل بأسبوعين» → Beena تفلتر ملايين المنتجات وتعرض المنتقى فقط داخل الشات.

🎁

Pre-order / تمويل جماعي

منتج غالي الشحن يُطلب جماعياً؛ عند بلوغ عدد معيّن تُشحن الدفعة بسعر أرخص للجميع — يرفع الهامش ويقلّل الكلفة.
